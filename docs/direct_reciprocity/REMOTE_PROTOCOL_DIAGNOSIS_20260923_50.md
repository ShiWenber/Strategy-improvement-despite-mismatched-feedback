## 对常见解释的核查

1. **客户端读取超时不符合证据。** 本轮配置为 `httpx.Timeout(3600, connect=30)`；HTTPX 的读取超时针对等待下一块数据的时间，不是整个任务的总耗时。本轮记录的是 RemoteProtocolError，而非 ReadTimeout。许多失败在刚有输出后出现。单纯提高该超时没有针对已发现的故障机制。
2. **官方“10 分钟关闭”规则不适用于这些已开始推理的请求。** 官方描述的条件是十分钟后仍未开始推理；本轮失败流已经包含大量 reasoning_content。失败时长分散，且部分成功请求持续超过十分钟。
3. **没有标准并发限流证据。** 官方当前文档列出 deepseek-flash 并发上限 2500，超限表现为 HTTP 429；本轮本地并发上限 50，16 条均已开始流式返回，未保存 429。账户其他任务负载未知，因此不能完全排除账户或服务负载参与，但不能认定“50 并发超过限额”。
4. **没有输出上限耗尽的记录。** 配置上限 384000；失败流没有 length 标记。没有最终 usage，无法确定失败请求准确 token 数，也不能把字符数或块数充当 token 数。成功请求的输出远低于上限，但这不构成失败请求用量的直接证据。
5. **不是已经观察到的策略执行错误。** 16 条均无最终代码，尚未进入这些候选的代码验证和博弈运行。
6. **没有本轮本地文件权限错误证据。** 本轮失败类别中没有 PermissionError/OSError；已保存文件均能读取。调查时 C 盘有约 248 GB 空闲；这只是事后状态，不能代替当时磁盘性能监控。
7. **没有发现显式 HTTP 代理配置。** 调查进程加载相同 dotenv 后，Python 的环境/Windows 注册表代理发现返回空。该事后检查不排除透明代理、VPN、网络设备或服务端网关，也不是已退出进程环境的完整快照。

## 日志缺失导致的定位障碍

`thinking_control.py` 的捕获分支只保存异常类型、可选状态码和可选提供方错误对象，随后 `raise RuntimeError(...) from None`。本轮 16 条的 http_status 均为 null，这表示异常对象未提供该属性，不表示服务端没有发送响应头。

因此丢失了原始 `str(exc)`、异常 cause/context 链、原始 traceback、HTTP 响应头和实际协议版本。外层 stderr 只有汇总 RuntimeError。已经丢失的异常信息无法通过重新解析 JSONL 恢复。

本地依赖版本：openai 2.40.0、httpx 0.28.1、httpcore 1.0.9、h11 0.16.0。执行器未指定 HTTP/2，HTTPX 默认关闭 HTTP/2。查阅本机 httpcore/h11 代码发现，HTTP/1.1 响应体未正常结束即收到 EOF 会触发 RemoteProtocolError；非法分块也可能映射成该异常。这解释了可能的机制，不等于已观测到具体异常消息。

每个请求使用自己的客户端，因此本轮不是 50 个请求共用一个默认连接池导致的池额度不足。流中的 SSE 注释由 SDK 解析器处理；当前 JSONL 不保留这类注释，不能据此统计保活次数。
